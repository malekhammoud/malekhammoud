# Programmatic SEO — plan

**Goal:** drive search traffic that converts into paid work on private/self-hosted AI
systems. Not traffic for its own sake.

**Status:** not started. This document is the whole plan; it assumes you are
reading it cold on the VPS with no memory of the conversation that produced it.

**Generation model:** [build.nvidia.com](https://build.nvidia.com) (NVIDIA NIM),
free tier, OpenAI-compatible API.

---

## 0. Read this first: what happened last time

Between 2026-02-27 and 2026-04-29 this repo ran a programmatic SEO experiment
that produced **1,400 pages** at `/software/<tool-a>-vs-<tool-b>` — SaaS
comparison pages generated by pairing 551 tools within 203 categories from a
SQLite database. It was dripped 25/day by a GitHub Actions cron and then deleted
in commit `f532c41`.

Recover any of it with:

```bash
git show f532c41^:scripts/generate_mdx.mjs          # the generator
git show f532c41^:.github/workflows/drip-deploy.yml # the cron
git show f532c41^:scripts/saas_data.db > /tmp/saas.db
git ls-tree -r --name-only f532c41^ | grep '^src/app/software/'
```

### Three parts of it were good and are being reused

1. **The drip.** Pages waited in `_stash/` and moved 25/day into the live
   directory. Publishing hundreds of pages at once onto a low-authority domain
   is the pattern that gets sites flagged. This was right.
2. **The smart link resolver** (`scripts/smart_deploy.mjs`, still in the repo).
   On every deploy it rewrites each page's "Explore More" block, commenting out
   links to pages that aren't live yet and uncommenting them once they are. A
   real internal-link graph that never 404s mid-rollout.
3. **IndexNow on deploy** (`scripts/ping_indexnow.mjs`, still in the repo, with
   the key-verification route at `src/app/[key]/route.ts`).

### Five reasons it could not have worked

Ranked by how much each mattered.

1. **There was no conversion path.** `/software` had its own layout
   (`SoftwareLayoutWrapper.jsx`) with a "Back to Software Hub" link and a
   copyright line. No site nav, no offer, no contact link, no CTA on any of the
   1,400 pages. Even at #1 for everything, that traffic converts at zero. This
   is the single most important lesson in this document.
2. **The audience was not the buyer.** Someone searching "1Password vs
   Bitwarden" is shopping for a password manager. The overlap with "companies
   that can't send data to OpenAI" is noise.
3. **No first-hand knowledge.** The generator fed a description, a price and a
   feature list to a free model and asked for a comparison. Nothing on those
   pages wasn't already on the vendors' own pricing pages.
4. **Unwinnable competitive set.** "1password vs bitwarden" belongs to G2,
   Capterra, PCMag and the vendors. Meanwhile the tail was worse: a cartesian
   product within category produced pages like
   `snipfeed-vs-wesselga-rden-brygghus`, which nobody has ever typed.
   **Combinatorial generation creates pages faster than it creates demand.**
5. **Policy risk.** Since March 2024 Google's "scaled content abuse" policy
   names this shape directly. The downside is a site-wide signal, not just
   pages that fail to rank.

### The old URLs

The 1,400 `/software/*` URLs now 404. **Leave them.** A 404 is the correct
signal for removed thin content. Do not redirect them to `/work` — that passes
exactly the association you don't want.

## 1. The rule everything below follows

The old system generated **prose about things**. This one generates **data about
things**.

> A programmatic page earns its existence when it contains a computed or
> measured fact the searcher cannot get at a glance anywhere else.

Prose is infinitely reproducible and therefore worth nothing at scale. A number
you calculated or measured is not.

**The architectural consequence, and the most important line in this file:**

> **Facts come from the HuggingFace API and from arithmetic. The LLM writes only
> connective prose, and only where prose adds something.**

That is the exact inversion of the old pipeline, where the model invented
everything including the facts. It is what makes the output accurate, and it is
what keeps this on the right side of the scaled-content-abuse line.

## 2. What gets built

The core question the target buyer actually types:

> *"Can I run Qwen 2.5 32B on a Mac Mini with 32GB?"*
> *"How much VRAM does Llama 3.3 70B need?"*
> *"What hardware do I need to self-host an LLM?"*

These are searched constantly, the answers live in scattered Reddit threads and
HuggingFace comments, and nobody publishes them systematically. Critically:
**anyone asking this is by definition trying to self-host a model.** That is the
buyer, at the moment they have the problem.

One dataset, three page types:

| Route | Approx. count | Contents |
|---|---|---|
| `/models/[slug]` | ~150 | Per model: size at every quantisation, minimum hardware, licence, context window, self-host vs API cost. |
| `/can-i-run/[model]-on-[hardware]` | ~300–500 | The direct-match query. **Only** generated for combinations that pass the demand gate in §6. |
| `/tools/*` | a handful | Calculators reading the same dataset. `/tools/llm-cost-calculator` already exists; a "will it fit" sizer is the obvious second. |

Adding a model adds pages everywhere automatically. Updating a number updates
every page that cites it.

### Alongside it: hand-written, high-intent pages

Ten to twenty, **not programmatic**, aimed at the person whose lawyer already
said no. Low volume, extraordinary intent, and they convert at rates no
comparison page ever will.

- "Is ChatGPT PIPEDA compliant?"
- "PHIPA and AI: what Ontario clinics can actually use"
- "Self-hosted alternative to the OpenAI API"
- "AI data residency in Canada"

These go in `/articles` as normal MDX. Write them yourself. Do not generate them
— they touch legal nuance, and getting one wrong costs more than all the traffic
is worth. State facts and cite the regulation; never give legal advice.

## 3. The data model

### 3.1 Where the facts come from

| Fact | Source | Method |
|---|---|---|
| Model list, popularity | HuggingFace API | `GET /api/models?filter=text-generation&sort=downloads` |
| Architecture (layers, heads, hidden size) | HF `config.json` | `GET /<repo>/raw/main/config.json` |
| **Size at each quantisation** | **HF file listing** | `GET /api/models/<repo>?files_metadata=true` → real GGUF byte sizes |
| Licence, context length | HF model card / config | API |
| Measured tokens/sec | **You, on your own hardware** | see §3.4 |

**Use real GGUF file sizes, not an estimate from a bits-per-weight table.** The
byte size of `qwen2.5-32b-instruct-q4_k_m.gguf` on HuggingFace is a fact. A
formula approximating it is not. The API returns it directly. This is the single
biggest accuracy advantage available and it costs one extra request.

Keep a bits-per-weight table only as a *fallback* for models with no GGUF
release, and label those figures as estimates on the page.

### 3.2 The one thing you must compute: KV cache

Weights are only half the memory. The KV cache scales with context length and is
what actually decides whether a long-context session fits.

```
kv_bytes = 2                    # K and V
         × n_layers
         × n_kv_heads           # NOT n_attention_heads — GQA models differ a lot
         × head_dim             # = hidden_size / n_attention_heads
         × context_length
         × bytes_per_element    # 2 for fp16 cache, 1 for q8 cache
```

Every input comes from `config.json`:

| Formula term | `config.json` key |
|---|---|
| `n_layers` | `num_hidden_layers` |
| `n_kv_heads` | `num_key_value_heads` (falls back to `num_attention_heads`) |
| `head_dim` | `head_dim`, else `hidden_size / num_attention_heads` |
| `context_length` | `max_position_embeddings` (cap the displayed default at something realistic, e.g. 8k, and show a slider/table for more) |

**`num_key_value_heads` is the term people get wrong.** Grouped-query attention
models have far fewer KV heads than attention heads, and using the wrong one
overstates the cache by 4–8×. Getting this right is a large part of why these
pages will be better than what's out there.

### 3.3 Total

```
total = gguf_file_bytes
      + kv_bytes
      + overhead        # runtime + activations; ~1.0–1.5 GB is a fair constant
```

Report in GB (base 1024) and state the assumption inline. Show the context
length the figure assumes — a number without its context length is meaningless
and that's exactly the mistake the existing scattered answers make.

### 3.4 The unfair data

For every model you **actually run**, record and publish:

- measured tokens/sec (prefill and decode separately if you can)
- real resident memory
- the exact hardware and quantisation

Mark these clearly as measured rather than computed. This is the most linkable
fact you own and the thing no competitor can copy. Even ten measured models is
enough to be the best page on the internet for those ten.

There is already a `TODO(Malek)` waiting on this in
`src/app/(main)/articles/self-hosting-llm-mac-mini/page.mdx`.

### 3.5 Hardware table

Hand-maintained, ~30–40 rows. Fields: name, slug, memory GB, memory type
(unified/VRAM/system), approximate bandwidth, notes.

Cover at minimum: Mac Mini M4 (16/24/32/64), Mac Studio (M4 Max, M3 Ultra),
MacBook Pro configs, RTX 3060 12GB, 3090, 4070 Ti, 4080, 4090, 5090, A4000,
A6000, L4, L40S, A100 40/80, H100, plus "64GB system RAM, CPU only".

Bandwidth matters as much as capacity for tokens/sec and almost nobody mentions
it. Including it is a differentiator.

### 3.6 Storage

SQLite at `data/models.db`, committed to the repo. It worked last time, it's a
single file, and it makes the build reproducible without network access.

Suggested tables:

```sql
CREATE TABLE models (
  slug TEXT PRIMARY KEY,
  hf_repo TEXT NOT NULL,
  name TEXT NOT NULL,
  family TEXT,              -- llama, qwen, mistral, gemma, deepseek…
  params_b REAL,            -- 32.5
  licence TEXT,
  context_length INTEGER,
  n_layers INTEGER,
  n_kv_heads INTEGER,
  head_dim INTEGER,
  hf_downloads INTEGER,     -- the demand proxy, see §6
  released DATE,
  refreshed_at DATETIME
);

CREATE TABLE quantisations (
  model_slug TEXT, quant TEXT,    -- Q4_K_M, Q5_K_M, Q8_0, fp16…
  file_bytes INTEGER,             -- REAL size from HF, not an estimate
  estimated BOOLEAN DEFAULT 0,    -- 1 when no GGUF exists and we fell back
  PRIMARY KEY (model_slug, quant)
);

CREATE TABLE hardware (
  slug TEXT PRIMARY KEY, name TEXT, memory_gb REAL,
  memory_type TEXT, bandwidth_gbs REAL, notes TEXT
);

CREATE TABLE measurements (          -- §3.4, hand-entered, the moat
  model_slug TEXT, hardware_slug TEXT, quant TEXT,
  tokens_per_sec REAL, resident_gb REAL, measured_on DATE, notes TEXT
);

CREATE TABLE pages (                 -- what has shipped, for the drip + prune
  route TEXT PRIMARY KEY, kind TEXT, published_at DATETIME,
  gsc_impressions INTEGER DEFAULT 0, gsc_checked_at DATETIME
);
```

## 4. Generation with build.nvidia.com

### 4.1 Setup

```bash
export NVIDIA_API_KEY=nvapi-...
```

OpenAI-compatible, so use the `openai` package with the base URL overridden:

```js
import OpenAI from 'openai'

const client = new OpenAI({
  apiKey: process.env.NVIDIA_API_KEY,
  baseURL: 'https://integrate.api.nvidia.com/v1',
})

const res = await client.chat.completions.create({
  model: 'meta/llama-3.3-70b-instruct',   // verify against the live catalogue
  messages: [{ role: 'system', content: SYSTEM }, { role: 'user', content: prompt }],
  temperature: 0.4,
  max_tokens: 900,
})
```

**Check the model catalogue at build.nvidia.com before you start** — it changes,
and the free tier has rate limits. The limits are a fit for the drip, not a
problem with it: you need 25 pages/day, not 1,400 in an afternoon.

### 4.2 What the model is and isn't allowed to write

This is the part that decides whether the project works.

**The LLM writes:**
- a 2–3 sentence "what this model is good at" summary per model
- a one-paragraph verdict per can-i-run page, given the computed numbers
- nothing else

**The LLM never writes:**
- any number
- any memory figure, price, licence, context length or benchmark
- the comparison table

Every number is interpolated from the database by the template, in code, after
generation. If a number can appear in the output of the language model, the
architecture is wrong.

### 4.3 Prompt shape

```
SYSTEM:
You write short, factual technical copy for an engineering reference site.
Plain and specific. No marketing adjectives. Never use: leverage, cutting-edge,
seamless, revolutionize, powerful, robust, game-changing.
Never state a number — numbers are inserted by the template. If you need to
refer to a quantity, write it as a placeholder like {{MEMORY}}.
Two to three sentences. No headings, no lists, no preamble.

USER:
Model: {name} ({params_b}B parameters, {family} family, {licence})
Trained for: {tags from HF}
Write the "what this is good at and who should use it" paragraph.
```

Then run the output through a **numeral filter**: if the generated prose
contains a digit that isn't in an allow-list, reject it and regenerate. Cheap,
mechanical, and it makes the "no invented facts" rule enforced rather than
hoped-for.

### 4.4 Cost control

Generate once, cache in the DB (`models.summary_md`), and never regenerate
unless the model's facts change. The drip publishes from cache. You should be
making roughly 150 + 500 LLM calls total across the whole project, not per
deploy.

## 5. Page templates

Same MDX pattern as `/work` and `/articles`, so
`src/lib/caseStudies.js` is the shape to copy.

```
src/app/(main)/models/[slug]/page.jsx        # dynamic, generateStaticParams from DB
src/app/(main)/can-i-run/[combo]/page.jsx    # dynamic, generateStaticParams from DB
src/lib/models.js                            # DB reads + the memory maths
src/components/models/MemoryTable.jsx
src/components/models/FitVerdict.jsx
src/components/models/HardwarePicker.jsx     # client, for the sizer tool
data/models.db
scripts/models/fetch-hf.mjs                  # HF → DB
scripts/models/generate-prose.mjs            # NIM → DB (cached)
scripts/models/build-pages.mjs               # DB → _stash/
```

**Prefer `generateStaticParams` over writing 500 MDX files.** The old system
committed a file per page; a dynamic route reading the DB at build time gives
the same static output with none of the repo bloat, and updating a number
doesn't produce a 500-file diff. The drip then controls which slugs
`generateStaticParams` returns (see §7).

### Every template must include

- [ ] The computed memory table, with the context-length assumption stated
- [ ] "Measured on real hardware" block where a `measurements` row exists
- [ ] A **contextual** CTA — tied to that page's specific finding, not a banner:
      *"This needs 48 GB. That's a real deployment, not a laptop — I build these. Book a call."*
- [ ] Links to `/tools/llm-cost-calculator` and `/work/self-hosted-inference`
- [ ] `BreadcrumbList` JSON-LD (helper already exists in `src/components/JsonLd.jsx`)
- [ ] Canonical URL, OG tags
- [ ] Last-updated date, visible — freshness is the moat, show it

The path to money is **tool → model page → case study → contact**. `/work/self-hosted-inference`
and the cost calculator are already built and sit at the end of that chain.

## 6. The demand gate

The rule that would have prevented the last failure: **no page ships unless its
entity plausibly has search volume.** Never generate a full cartesian product.

Without paid keyword tools, three free proxies, in order of usefulness:

1. **HuggingFace download counts.** A model with 2M downloads has people
   searching for it; one with 400 does not. Publish `/models/*` ordered by
   downloads and stop at a threshold. This is a genuinely good proxy and it's
   free.
2. **Google autocomplete / "People also ask".** For `can-i-run` combos, check
   that "can i run <model> on" autocompletes at all. Scriptable against the
   suggest endpoint; be polite about rate.
3. **Search Console, once live.** After the first 100 pages, real impression
   data tells you which *shapes* work. Expand the shapes that earn impressions,
   drop the ones that don't.

For `can-i-run`, do not pair every model with every hardware. Pair the **top ~40
models** with the **top ~12 hardware configs**, then drop combinations that are
trivially absurd (a 405B model on a 12GB card — though a few "no, and here's
what you'd need instead" pages are genuinely useful and convert well, so keep a
handful deliberately).

## 9. Pruning

The step almost nobody does, and what separates a database from a content farm.

- [ ] Monthly job: pull GSC impressions per URL into `pages.gsc_impressions`
- [ ] Any page with **zero impressions after 90 days** gets deleted
- [ ] Any page whose model has been superseded gets refreshed or removed

Deleting pages that earn nothing improves the average quality of the site, which
is a thing Google measures. Keep the winners, cut the rest.

## 10. Freshness

Model data goes stale monthly. This is an advantage if automated — freshness is
a ranking signal and a moat against static competitors — and actively harmful if
not. A model database showing last year's lineup is worse than no database.

- [ ] Weekly `fetch-hf.mjs` run refreshing download counts and file sizes
- [ ] New models above the download threshold get queued automatically
- [ ] Visible "last updated" on every page

## 12. Expectations

- **~450 pages of real value**, not 1,400 of filler. If the count starts
  climbing toward four figures, something has gone wrong with the demand gate.
- **6–9 months** before compounding. This is not a quarter-long project.
- The **tools earn the links**, the **model pages capture the tail**, the
  **compliance articles convert**. Three different jobs; don't judge one by
  another's metric.
- The metric that matters is `booking_cta_clicked` in PostHog, segmented by
  landing page. Not sessions.

## 13. The checklist that would have saved the last attempt

Before any page ships, all five:

1. Does a real person type this query?
2. Does the page contain a number I computed or measured that isn't already on page one?
3. Is the person searching this plausibly a buyer?
4. **Is there a CTA on the page that makes sense given what this specific page says?**
5. Would I be happy for a prospective client to land here first?

If any answer is no, don't publish it.
