## The thesis

Can an autonomous AI agent run an end-to-end micro-SaaS business on a public cloud marketplace without human code intervention?

I built a closed-loop agent system and set it loose on a Linux server. Its mandate was to autonomously find regulatory data niches, engineer scrapers, validate schemas, configure pay-per-event monetization, and publish production data products to the [Apify Store](https://apify.com/malekh).

The result: **a fully autonomous agent engine that engineered, smoke-tested, and published 22 live production data products with zero human code changes.**

---

## What was built: The Autonomous Agent Architecture

Rather than writing scrapers manually, I built an **autonomous supervisor system** that orchestrated the entire lifecycle of a micro-SaaS data product.

```
┌──────────────────────────┐      ┌──────────────────────────┐      ┌──────────────────────────┐
│ 1. Demand Mining Engine  │ ───► │  2. Scraper Synthesis    │ ───► │  3. Smoke & Schema Guard │
│  (30d Volume & Rivals)   │      │ (Node.js + Liveness Canaries)  │ (Dry Runs & Schema Check) │
└──────────────────────────┘      └──────────────────────────┘      └────────────┬─────────────┘
                                                                                 │
┌──────────────────────────┐      ┌──────────────────────────┐                   │
│  6. Supervisor Sandbox   │ ◄─── │ 5. Cloud Deploy Pipeline │ ◄───────────────────┘
│ (Systemd + Circuit Stop) │      │ (2-Step API Publish)     │  4. Monetization Engine
└──────────────────────────┘      └──────────────────────────┘ (Pay-Per-Event Schema)
```

The system is composed of six core autonomous subsystems:

### 1. Market Mining & Demand Selection Engine
The agent polls marketplace search APIs and competitor metrics to evaluate queries. Rather than guessing niches, it evaluates empirical 30-day buyer volume (`demand_runs_30d >= 400`), targeting queries with active transaction flow.

### 2. Code & Schema Synthesis Engine
When a niche passes screening, the agent generates a complete Node.js / Apify SDK Actor from scratch. It builds:
- **The Core Scraper / API Handler:** Standardized on official APIs, Socrata/CKAN open data portals, and structured government endpoints.
- **Input & Output Schemas (`INPUT_SCHEMA.json`):** Strict JSON Schema definitions for user parameters and dataset outputs.
- **Liveness Canary Assertions:** Embedded assertions that verify data freshness floor and schema shape *before* execution succeeds.
- **SEO & Store Copy:** Generated `seoTitle`, `seoDescription`, and README documentation.

### 3. Smoke Testing & Pre-Flight Validation
Before deployment, the agent spawns an isolated local test execution. It runs non-billed dry tests to verify:
- Clean process exit codes (`0`) and zero unhandled rejections.
- JSON output schema compliance against expected data keys.
- Memory consumption within sandboxed boundaries.

### 4. Automated Monetization Engine
The agent programmatically designs Pay-Per-Event (PPE) pricing models via API. It configures multi-tier event pricing—charging a small liveness guard fee ($0.05–$0.50) alongside per-record determination fees ($0.02–$3.00), while passing platform compute costs through (`Pass platform costs: True`).

### 5. Two-Step Cloud Deployment Pipeline
Apify forbids creating a public actor directly via single API calls. The agent executes a 3-step publishing sequence using the Apify REST API:
1. `POST /v2/acts` — Creates a private actor containing inline source files and input schemas.
2. `POST /v2/acts/{id}/builds` — Triggers cloud container compilation and polls until build state reaches `READY`.
3. `PUT /v2/acts/{id}` — Injects the monetization schema payload and flips `isPublic: true` to publish live on the store.

### 6. Supervisor Sandbox & Circuit Breakers
The autonomous loop runs inside a transient `systemd` slice (`MemoryMax=900M`, `CPUWeight=20`). It enforces dual API key privilege separation (read-only metrics polling vs. ephemeral write tokens), enforces publishing rate limits (max 5/24h), and executes hard circuit breakers (`experiment_stop_reached()`).

## Unit economics: Pay-Per-Event pricing

All actors use Apify's **Pay-Per-Event (PPE)** model with platform compute cost pass-through. The agent structured pricing into a two-tier model:

1. **Liveness Guard Event ($0.05 – $0.50):** Charged only after data freshness and schema integrity pass. If a target site layout shifts or returns an HTTP error, the run aborts cleanly with **$0.00 billed**.
2. **Determination Event ($0.02 – $3.00):** Charged per verified entity or report returned, undercutting legacy manual vendors by **50x to 1,000x** while preserving an **80%+ gross margin**.

## The pivot: Scarcity vs. measured demand

The biggest strategic takeaway came from how the agent selected what to build.

<Callout title="Strategic Pivot">
  The agent originally picked targets using a <strong>scarcity screen</strong> (<code>supply &lt; 10</code> competitors). This proved wrong: low competition usually meant <em>zero buyer interest</em>. The agent pivoted to a <strong>measured demand screen</strong> (<code>demand_runs_30d &gt;= 400</code>), picking queries with proven marketplace volume.
</Callout>

To validate the pivot, the agent launched a controlled experiment: building 8 demand-proven Actors (like SEC Form D and OFAC Sanctions), triggering a hard-coded stop (`experiment_stop_reached()`), and locking a 14-day conversion baseline.

## Sandboxing & security hardening

Operating an autonomous coding agent on a live server requires strict boundaries:

- **Systemd Sandboxing:** The agent ran inside a `systemd` transient slice capped at `MemoryMax=900M` and `CPUWeight=20`. Any memory spike resulted in a clean process drop without affecting host services.
- **Dual API Key Isolation:** Read-only tokens for metric gathering, with write permissions granted strictly during build and deploy phases.
- **Incident Response:** When an unauthenticated local proxy was briefly exposed during iteration, systemd cgroups restricted host CPU impact to under $0.01. The agent terminated the process, rotated credentials, and locked network bounds automatically.

## Key lessons learned

1. **Scarcity is not opportunity.** If no one is building on a query, check if anyone is searching for it first.
2. **Sell determinations, not raw rows.** Buyers don't want a dataset dump—they pay for an answer to a compliance question.
3. **Canary guards prevent bill disputes.** Aborting runs before charging fees when a target site breaks protects vendor reputation.
4. **Hard boundaries enable safe autonomy.** Sandboxing memory and enforcing programmatic stop conditions keeps agents reliable.
