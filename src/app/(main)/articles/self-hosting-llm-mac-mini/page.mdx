Most writing about running your own language model stops at the interesting
part. Someone loads weights, gets a response in a terminal, screenshots it, and
publishes. That's the first afternoon. It tells you nothing about whether you
can build something on it.

This is about the rest of it.

## Why Apple Silicon at all

The default assumption is that self-hosting means an NVIDIA card, and for
training it does. For *inference* on a small-to-mid open-weight model, Apple
Silicon has one architectural advantage that matters more than raw throughput:
**unified memory**.

On a conventional machine, your model has to fit in VRAM. That's a separate,
smaller, much more expensive pool than system RAM, and the moment a model
doesn't fit you are buying a bigger card. On Apple Silicon the CPU and GPU
address the same memory, so "does it fit" is answered by how much RAM you
bought — and RAM is far cheaper per gigabyte than VRAM.

The practical consequence: a Mac Mini with a sensible memory configuration will
hold models that would otherwise require a discrete card costing several times
the price of the entire machine. It also draws tens of watts rather than
hundreds, runs close to silent, and can sit on a shelf in an office instead of
in a rack that needs cooling.

It is not the fastest option per dollar of hardware. It is frequently the most
*sensible* one for a single-tenant workload, which is what most internal
deployments actually are.

## MLX, and what quantisation is really trading

**MLX** is Apple's array framework, and `mlx-lm` is the piece that serves
language models with it. It is built for unified memory rather than adapted to
it, which is why it tends to beat the general-purpose runtimes on this hardware.

The lever that decides what you can run is **quantisation** — storing weights at
lower precision. It is usually described as a quality/size tradeoff, which is
true but unhelpfully vague. The useful framing is:

- Quantisation buys you **memory**, and memory is what decides whether you can
  run a larger model at all.
- A **larger model at lower precision** very often beats a smaller model at
  higher precision for the same memory budget.
- The quality cost is not uniform across tasks. Structured extraction and
  classification degrade gracefully. Long multi-step reasoning degrades first.

So the right question isn't "how much quality am I losing," it's "which model
fits my memory at a precision that still does *my specific job*." That's an
evaluation question, and it's why the first thing I build on a deployment is
usually the eval, not the service.

## The part nobody writes about

Here is the whole gap between a demo and a deployment. None of it is difficult.
All of it is necessary, and all of it gets skipped.

### It will crash

Inference processes die — bad input, memory pressure, an OS update, a power
blip. If a dead process means a dead product, you don't have a service.

You need something that notices and restarts it. On macOS that's `launchd`,
and the important detail is that it should restart on boot too, because the
machine *will* be power-cycled by someone who doesn't know what it does.

### It needs authentication

An unauthenticated model server on your network is not a feature. Anyone who
can reach the port can use your hardware, read whatever is in the context, and
run up your electricity bill. This is a token check — perhaps twenty lines —
and its absence is the single most common thing I find when I'm asked to look
at someone's existing setup.

### Loading a model per request is not viable

Model load time dwarfs inference time for anything short. Weights have to stay
resident between requests, which means the serving process is long-lived, which
means everything above about crashes applies.

If you need more than one model, switching should be a deliberate operation
with a known cost — not something a caller can trigger by accident on every
request.

### You will write a router

Eventually you want per-caller authentication, per-caller model selection,
request logging, and a stable interface that doesn't change when you swap the
model underneath. That is a router, and you will end up writing one whether or
not you planned to.

Mine is Python, sits in front of `mlx-lm`, and handles exactly those four
things. It is not clever. It is the difference between something I use and
something I can hand to someone else.

## Does it save money?

Sometimes. The arithmetic is genuinely simple: hosted inference is a per-token
cost that scales with usage, self-hosting is a fixed hardware cost plus
electricity that doesn't.

Two things the arithmetic leaves out, both of which matter more than the
number it produces:

**Your time.** Setup is a day or two if you know what you're doing and a week
if you're learning. Someone has to keep it running afterwards. That cost is
real and no calculator can price it for you.

**Whether the API was ever an option.** For a lot of the teams I work with,
sending data to a third party is ruled out by a client contract or a regulator
before anyone opens a pricing page. If that's your situation, the cost
comparison is a formality — you were always going to run it yourself, and the
only question is whether it's run well.

## Where I'd start

If you're evaluating this seriously, in order:

1. **Write the evaluation first.** Twenty real examples of your task with known
   correct answers. Without this you cannot tell whether a smaller model is
   fine, and that decision determines the hardware.
2. **Run the model on any machine you already have.** Confirm quality before
   spending anything.
3. **Size the hardware from the model**, not the other way round.
4. **Then build the boring parts** — auth, supervision, logging — because that
   is what turns it into something you can depend on.

Most people do this in exactly the reverse order, buy the machine first, and
discover at step one that they needed a different one.
